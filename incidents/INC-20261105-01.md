# 缺陷通報：CAN-FD CRC-17 算錯，而且量具（規格黃金向量）跟著錯

> 本通報採「流程檢討」格式：重點不是哪一行程式寫錯，而是哪一道管理流程讓錯誤能一路走到入庫。
>
> **結案範圍**：已完成圍堵（錯誤產品撤出函式庫）、量具校正與流程修正。重做產品屬於新的生產工單，由雲端農夫排程（`farm-queue` 下一個就是 `canfd_crc`），交貨時由 MSA 量具驗收，不再讓本通報保持未結。

## 1. 發生了什麼
- `src/canfd_crc.rs`（commit 2ce66df 入庫）把資料位元推進暫存器最低位、沒有乘 x^17，算出的是 M(x) mod G(x)，不是 CRC。用 `"123456789"` 算出 0x12380，公認值是 0x04F03（RevEng CRC 目錄）。和真實 CAN-FD 設備互通會失敗。
- 規格 `specs/canfd_crc.md` 的黃金向量是**照同一個錯誤演算法推出來的**，所以產品「通過了自己的考卷」。CI 全綠。

## 2. 走偏、疏漏，還是壓力崩潰？
- **疏漏（主因）**：規格的預期值沒有要求外部出處。出題者用自己寫的演算法推答案，題目和答案同源。量具從未拿「公認標準件」校正過，等於用沒校正過的尺驗貨。
- **走偏（次因）**：驗收只問「有沒有通過規格的測試」，沒問「測試本身可不可信」。這是把「照做」當成「做對」。
- **壓力崩潰**：無證據。農夫只嘗試一次就通過，沒有二振或紅燈紀錄，不是被逼出來的錯。

## 3. 是哪一步流程
規格撰寫 → 黃金向量（**量具在這裡就壞了**）→ 農夫生產 → golden 測試（用壞量具量）→ 入庫。

## 4. 流程怎麼改（本 PR）
1. **量具驗收先於產品驗收（MSA）**：高風險積木在 `msa/<模組>.rs` 放
   - 公開標準件（外部出處的公認值）和獨立的參考實作；
   - 挑戰件：已知錯誤寫法，包括本次實際入庫的錯誤版本。
2. **判讀規則**，由 `cargo run -- msa` 自動判定：
   - 標準件不過 → 🔴 量具壞了，產品不量測；
   - 挑戰件抓出率 < 70% 或容差比 > 30% → 🔴 量具重做；
   - 抓出率 70–90% 或容差比 10–30% → 🟡 需簽核；
   - 否則 🟢。
   - 量具可信時才量產品：黃金向量全過，且盲測（2000 筆規格外的隨機輸入，與參考實作比對）0 不一致，才 🟢 允收。
3. **農夫開工前先驗量具**：量具壞了就拒絕生產（outcome `gauge-broken`），不呼叫模型、不浪費額度。
4. **重現性**：CI 在 ubuntu x86、windows、ubuntu arm 三個平台各量一次。
5. **規格黃金向量逐行標 `@source`**：寫明外部出處，不得用規格本身的演算法推算。

## 5. 怎麼知道有效
試點實測，可在本 PR 重跑：
- 舊規格＋舊產品：🔴 量具壞了（標準件 #2、#7 不過；挑戰件「no_augment」沒抓到）。**證明新流程能抓到這次的事故。**
- 校正後量具＋舊產品：🟢 量具 5/5 挑戰件全抓到；🔴 產品拒收（盲測 1888/2000 不一致）。
- 撤出產品後：🟢 量具、⚪ 產品未量測，農夫排程重做。
- 模擬重做：第 1 次錯誤寫法被 golden #1 擋下；第 2 次正確寫法 → 🟢 允收（盲測 0/2000）。
- 拿舊規格叫農夫重做：拒絕開工（`gauge-broken`），沒有呼叫模型。
